INKNOTE AI - DETAILED PROJECT ARCHITECTURE GUIDE
=================================================

This document explains how the current InkNote AI project works. It is divided into
two main parts:

  PART I  - BACKEND
  PART II - FRONTEND

The final section shows complete request flows and safe extension points.


PROJECT OVERVIEW
================

InkNote is a local-first, multimodal notebook application. A user writes or draws on
one shared canvas and presses Send. A Qwen vision model interprets the page and chooses
one of four routes:

  chat     - Return a written answer.
  image    - Generate an image with FLUX.
  both     - Return written content and a generated image.
  clarify  - Ask the user what they intended.

The application uses:

  FastAPI                         HTTP server and API
  SQLite                          Note titles and visible UI blocks
  JSON files                      Qwen conversation histories
  Ollama qwen2.5vl:3b             Vision routing and chat
  Ollama qwen3-embedding:0.6b     Semantic-memory embeddings
  FLUX.2 Klein 4B                 Local image generation
  Vanilla HTML/CSS/JavaScript     Browser interface
  Canvas 2D API                   Pen, eraser, and handwriting surface

Important current behavior:

  * Notebook handwriting is analyzed by Qwen.
  * Raw notebook pixels are NOT passed to FLUX. This prevents handwritten
    instructions from being copied into generated images.
  * FLUX receives a cleaned, text-only visual description from Qwen.
  * Image-only requests return an image without a hardcoded text acknowledgement.
  * The browser provides Low, Medium, and High image quality choices. Internally
    these map to 10, 25, and 50 inference steps.


===============================================================================
PART I - BACKEND
===============================================================================


1. BACKEND FILE MAP
===================

backend/app.py
  Creates the FastAPI application, defines request schemas and API routes, mounts
  static/generated files, and performs startup initialization.

backend/config.py
  Loads .env and exposes all paths, model identifiers, memory settings, and image
  generation settings.

backend/agents/canvas_agent.py
  Coordinates a complete canvas request. It invokes the vision router, chooses chat
  and/or image generation, records responses, and builds the API result.

backend/services/image_generation.py
  Decodes the canvas, asks Qwen to analyze it, loads/releases FLUX, cleans the FLUX
  prompt, runs inference, and saves generated PNG files.

backend/agents/agent.py
  Implements normal Qwen chat, context-window construction, semantic-memory lookup,
  conversation locking, and history recording.

backend/services/llm.py
  Small streaming wrapper around ollama.chat for normal text responses.

backend/services/semantic_memory.py
  Extracts durable user facts, embeds them, performs cosine-similarity search, and
  stores semantic memory in JSON.

backend/storage/store_history.py
  Reads and atomically writes per-note Qwen conversation files.

backend/storage/note_store.py
  Implements SQLite CRUD operations for notes and their visible frontend blocks.

requirements.txt
  Python package requirements, including the CUDA 13.0 PyTorch wheels.

run_windows.bat
  Windows launcher. It verifies .venv, creates .env from .env.example when needed,
  activates the virtual environment, and starts Uvicorn.


2. APPLICATION STARTUP
======================

The usual entry point is:

  run_windows.bat

The launcher performs these operations:

  1. Check that .venv\Scripts\python.exe exists.
  2. Copy .env.example to .env if .env is missing.
  3. Activate the virtual environment.
  4. Start Uvicorn with reload enabled on port 8000.

backend/app.py imports torch before FastAPI. This ordering is intentional on Windows because
PyTorch's native DLLs should be loaded before FastAPI begins using worker threads.

FastAPI then enters its lifespan function:

  1. init_database()
  2. Create data/generated when missing.
  3. Start accepting requests.


3. CONFIGURATION
================

backend/config.py loads values from .env. Important defaults are:

  INKNOTE_CHAT_MODEL=qwen2.5vl:3b
  INKNOTE_MULTIMODAL_MODEL=qwen2.5vl:3b
  INKNOTE_EMBEDDING_MODEL=qwen3-embedding:0.6b
  INKNOTE_IMAGE_PROVIDER=flux2_local
  INKNOTE_IMAGE_MODEL=black-forest-labs/FLUX.2-klein-4B
  INKNOTE_IMAGE_DEVICE=cuda
  INKNOTE_IMAGE_DTYPE=bfloat16
  INKNOTE_IMAGE_CPU_OFFLOAD=true
  INKNOTE_IMAGE_RELEASE_AFTER_GENERATION=true

The local .env currently may override release-after-generation for faster repeated
generation. .env is ignored by source control and must never be committed with a real
Hugging Face token.

Important data paths:

  data/inknote.db                SQLite note database
  data/conversations/*.json     Qwen message histories
  data/memory/knowledge.json    Semantic memories and embeddings
  data/generated/*.png          Generated FLUX images
  frontend/                     Browser assets


4. MANUAL MODEL PROVISIONING
============================

The project does not install, verify, or download models automatically.

Before startup, install Ollama and manually pull:

  ollama pull qwen2.5vl:3b
  ollama pull qwen3-embedding:0.6b

Download black-forest-labs/FLUX.2-klein-4B into the standard Hugging Face cache
with the hf CLI or huggingface_hub.snapshot_download(). The image service uses
local_files_only=True, so a missing cache produces an error instead of a download.

See README.md for complete installation, authentication, and verification steps.


5. FASTAPI ROUTES
=================

Static routes:

  GET /
    Returns frontend/index.html.

  GET /manifest.webmanifest
    Returns the PWA manifest.

  GET /service-worker.js
    Returns the service worker with the correct JavaScript media type.

Static mounts:

  /static
    CSS, JavaScript, icon, and other browser assets.

  /generated
    Saved FLUX PNG images.

Health route:

  GET /api/health
    Returns server status, chat model, multimodal model, image availability, and
    configured FLUX model.

Note routes:

  GET    /api/notes
  POST   /api/notes
  GET    /api/notes/{note_id}
  PUT    /api/notes/{note_id}
  DELETE /api/notes/{note_id}

Canvas route:

  POST /api/canvas/submit

CanvasSubmitRequest contains:

  note_id
    1-100 letters, numbers, underscores, or hyphens.

  page_data_url
    Base64 image data URL, limited to 15 MB.

  strokes
    Array of vector stroke objects, limited to 20,000 entries.

  inference_steps
    Server-validated value: 10, 25, or 50.


6. CANVAS REQUEST ROUTING
=========================

canvas_agent.process_canvas_submission() is the main backend coordinator.

Step 1 - Analyze the notebook

  analyze_canvas_page() receives the white-background PNG and stroke count.
  It sends the image to qwen2.5vl through Ollama using a strict JSON schema.

  Expected analysis fields:

    action
    confidence
    recognized_text
    display_text
    conversation_message
    image_prompt
    clarification_question

Step 2 - Apply confidence rules

  If confidence is lower than INKNOTE_ROUTER_CONFIDENCE_THRESHOLD, the route becomes
  clarify. Image/both routes also become clarify when image_prompt is empty.

Step 3 - Execute the selected route

  chat:
    Calls agent.process_user_message(). Qwen returns a normal written response and
    the exchange is saved.

  image:
    Calls generate_canvas_image(). No chat response is generated. On success the API
    returns image_url and text_response remains null.

  both:
    First calls Qwen with IMAGE_TOOL_CONTEXT for only the separately requested written
    content. Then calls FLUX. The Qwen text and generated image share the same turn.

  clarify:
    Returns the router's clarification question and records it.

Step 4 - Return a normalized response

  The result contains:

    intent
    confidence
    user_text
    text_response
    image_url
    image_prompt
    inference_steps

There is currently no hardcoded "I've generated the image" message.


7. QWEN VISION ANALYSIS
=======================

image_generation.analyze_canvas_page() performs vision routing.

Processing:

  1. Validate and decode the base64 data URL.
  2. Convert it to RGB with Pillow.
  3. Limit the image to 1536 x 1536 while preserving aspect ratio.
  4. Encode it as PNG bytes.
  5. Call ollama.chat with the configured multimodal model.
  6. Require structured JSON output.
  7. Normalize confidence and strings.

The router prompt tells Qwen:

  * A drawing alone does not automatically mean image generation.
  * Explicit creation/transformation language routes to image.
  * "both" is only used when text and image are both requested.
  * image_prompt must be a positive visual scene description.
  * Handwritten instructions and typography terms must not be placed in image_prompt.
  * Generated notebook images are intentionally text-free.


8. CHAT AGENT AND CONVERSATION CONTEXT
======================================

agent.process_user_message() uses one lock per conversation/note ID. This prevents two
requests for the same note from writing history simultaneously.

For each request:

  1. Strip and validate the user's text.
  2. Load conversation history, beginning with SYSTEM_MESSAGE.
  3. Search semantic memory for relevant facts.
  4. Append the new user message.
  5. Keep only the configured number of recent context messages.
  6. Insert relevant memory and optional tool context.
  7. Stream text chunks from llm.ask_model().
  8. Save the assistant response when record=True.
  9. Start background memory extraction.

For a "both" canvas route, record=False is used during Qwen generation so the final
combined exchange is saved once by record_exchange().


9. SEMANTIC MEMORY
==================

Semantic memory is separate from normal conversation history.

extract_memories():
  Asks Qwen to return durable facts such as user preferences, skills, projects, or
  long-term goals. Temporary facts and ordinary questions should be ignored.

create_embedding():
  Uses qwen3-embedding:0.6b through Ollama.

add_memory():
  Avoids exact duplicate text, stores the text, its vector, and embedding-model name.

search_memories():
  Embeds the current query, calculates cosine similarity, and returns up to three
  memories scoring at least 0.35.

Memory writes use a temporary file followed by replace, preventing partially written
JSON from becoming the live memory file.


10. FLUX IMAGE GENERATION
=========================

generate_canvas_image() receives only:

  image_prompt
  recognized_text
  num_inference_steps

It does not receive the raw notebook image.

Prompt cleaning:

  clean_flux_prompt() removes any recognized handwritten text that appears verbatim
  in Qwen's image prompt. It also collapses whitespace and rejects an empty result.

Pipeline loading:

  * Flux2KleinPipeline.from_pretrained()
  * local_files_only=True
  * dtype comes from .env
  * low_cpu_mem_usage=True
  * optional Hugging Face token
  * model CPU offload when configured

The model installer ensures the repository is cached before this local-only load.

Generation settings:

  width=1024
  height=1024
  guidance_scale=1.0
  num_inference_steps=10, 25, or 50

Concurrency:

  _PIPELINE_LOCK protects one-time pipeline loading.
  _GENERATION_LOCK allows only one FLUX inference at a time.

Output:

  A UUID filename is created under data/generated.
  The image is saved as PNG.
  The API returns /generated/{uuid}.png.

When IMAGE_RELEASE_AFTER_GENERATION is true, the pipeline reference is discarded,
Python garbage collection runs, and the CUDA cache is cleared.


11. BACKEND PERSISTENCE
=======================

There are three independent persistence layers.

A. Visible notes - SQLite

  Table: notes

  Columns:
    id
    title
    blocks_json
    created_at
    updated_at

  blocks_json contains the frontend's visible conversation blocks. SQLite is the
  source used to rebuild the note list, AI canvas, and conversation dock.

B. Qwen history - JSON

  One file per note ID under data/conversations.
  These files contain role/content messages used as model context.

  IDs are checked against:
    ^[A-Za-z0-9_-]{1,100}$

  Writes are atomic through a temporary .tmp file followed by replace.

C. Semantic memory - JSON

  data/memory/knowledge.json stores durable facts and embedding vectors.

Deleting a note removes:

  * Its SQLite row.
  * Its Qwen conversation-history JSON.

Generated PNG files are not automatically deleted with their note.


12. BACKEND ERROR AND SAFETY BEHAVIOR
=====================================

  * Pydantic validates API payload sizes and inference-step values.
  * Missing notes return HTTP 404.
  * Invalid data URLs raise a clear error.
  * Missing Ollama produces a model-setup error.
  * Missing FLUX triggers automatic download when enabled.
  * Image generation is serialized by a lock.
  * Conversation writes are serialized per note.
  * Sensitive .env values are excluded through .gitignore.
  * FLUX never receives notebook pixels, preventing prompt text from being copied.

frontend/index.html

frontend/css/styles.css

frontend/js/app.js

frontend/manifest.webmanifest
  Installable-web-app metadata.

frontend/icons/icon.svg

2. PAGE LAYOUT
==============

The page is organized into:

Sidebar:
  Brand, New note button, note list, connection status, and model names.

Top note header:
  Editable title, save status, Clear page, and Delete note.

User canvas panel:
  Pen/eraser controls, undo/redo, Clear, line-layout toggle, color palette, custom
  color picker, quality selector, Send, processing overlay, and scrollable canvas.

AI canvas panel:
  Shows only the most recent completed response turn. A response may contain text,
  an image, or both.

Conversation dock:
  Shows the saved chronological history for the active note.


3. FRONTEND STATE MODEL
=======================

The main state object contains:

  notes
    Summary list used by the sidebar.

  note
    Full active note, including its blocks array.

  saveTimer
    Debounce timer for note persistence.

  toastTimer
    Current notification timer.

  busy
    Prevents drawing, sending, switching tools, or changing generation quality while
    a canvas request is running.

Block objects contain:

  id
  type
  created_at
  turn_id (for request/response grouping)
  plus type-specific fields

Important block types:

  user_canvas
  assistant_text
  assistant_image
  error

assistant_image blocks contain:

  url
  prompt


4. DRAWING ENGINE
=================

CanvasPad is the browser drawing engine.

High-DPI handling:

  A ResizeObserver watches the canvas wrapper. The physical canvas size is multiplied
  by devicePixelRatio, capped at 3. The drawing context transform keeps stroke
  coordinates in CSS pixels.

Pointer handling:

  pointerdown starts a stroke.
  pointermove consumes coalesced pointer events when available.
  pointerup stores the completed stroke.
  pointercancel safely ends the stroke.

Each stroke stores:

  tool
  color
  width
  pointerType
  points

Each point stores:

  x
  y
  pressure
  timestamp while drawing

Pressure:

  Pen width is multiplied by a pressure-derived value. Mouse input falls back to 0.5.

Eraser:

  Uses CanvasRenderingContext2D.globalCompositeOperation="destination-out".

Undo and redo:

  Operate on entire stroke objects, not individual pixels.


5. CANVAS EXPORT AND FADE
=========================

toDataURL():

  1. Creates a temporary export canvas.
  2. Fills it with solid white.
  3. Draws the transparent live canvas over it.
  4. Returns a PNG data URL.

Notebook lines are CSS-only and are not embedded in the submitted image.

startFade():

  After Send, the current strokes fade over 650 ms using smoothstep interpolation.
  At completion, the stroke and redo arrays are cleared.

If submission fails, the saved structuredClone snapshot is restored so the user's
work is not lost.


6. CANVAS TOOLS AND PREFERENCES
===============================

Pen colors:

  Six preset swatches plus one custom HSV picker.

Custom picker:

  A two-dimensional field combines saturation and value.
  A separate slider controls hue.
  Pointer and keyboard input are supported.

Notebook layout:

  Lines on  - ruled notebook background.
  Lines off - solid white drawing surface.

  The preference is stored in localStorage under:
    inknote-canvas-lines

Image quality:

  Low
  Medium
  High

  The browser stores the underlying inference value in localStorage under:
    inknote-inference-steps

  Internal values:
    Low    = 10
    Medium = 25
    High   = 50

Only the friendly quality names are shown in the UI.


7. SUBMISSION FLOW
==================

submitCanvas() performs the complete frontend request.

Before the request:

  1. Reject when already busy, no note is selected, or no pen stroke exists.
  2. Generate a turn ID.
  3. Snapshot strokes for error recovery.
  4. Export a white-background PNG.
  5. Export vector strokes.
  6. Read the selected inference quality.
  7. Add pending user and assistant blocks.
  8. Lock the UI and start the canvas fade.
  9. Show the processing overlay.

API body:

  {
    "note_id": "...",
    "page_data_url": "data:image/png;base64,...",
    "strokes": [...],
    "inference_steps": 10 | 25 | 50
  }

During a slow request:

  After nine seconds, the status changes from routing to image-generation quality.

After success:

  1. Update the pending user block with Qwen's display text.
  2. Convert text_response into an assistant_text block when present.
  3. Remove the pending text block for image-only responses.
  4. Add assistant_image when image_url is present.
  5. Update the conversation dock.
  6. Replace and animate the AI canvas response.
  7. Update the route/quality hint.
  8. Unlock the UI and queue a save.

After failure:

  1. Convert the pending response to an error block.
  2. Restore the original strokes.
  3. Render the error.
  4. Show a toast.
  5. Unlock the UI and queue a save.


8. RESPONSE RENDERING
=====================

The AI canvas shows the latest response turn rather than the entire history.

latestResponseBlocks():

  1. Filters completed assistant text, image, and error blocks.
  2. Finds the most recent response.
  3. Returns every response block sharing its turn_id.

This allows a "both" response to display its text and image together.

The conversation dock independently displays all saved blocks in chronological order.


9. TEXT AND IMAGE ANIMATION
===========================

Text:

  animateDiaryText() splits text into whitespace, words, and punctuation. Tokens fade
  in with timing pauses based on token type. Punctuation pauses longer than spaces.

Images:

  animateImageReveal() waits for the image to load or error, then fades the entire
  image block in using the same smoothstep style. Reduced-motion preferences are
  respected.

Response replacement:

  The previous AI response fades out first. The new text and image animations then
  run together through Promise.all().


10. GENERATED IMAGE DOWNLOAD
============================

Each generated image is placed inside .assistant-image-frame.

An icon-only anchor is overlaid in the top-right corner:

  class="image-download-button"
  href=image URL
  download=generated PNG filename

It includes:

  * Inline SVG download icon.
  * Accessible aria-label.
  * Tooltip title.
  * Keyboard focus styling.

Because /generated is same-origin, the browser can directly download the PNG.


11. NOTE MANAGEMENT AND AUTOSAVE
================================

On startup:

  1. GET /api/notes.
  2. Create "My first InkNote" when no notes exist.
  3. Select the newest note.

Editing a title or changing blocks calls queueSave().

queueSave():

  * Displays "Saving".
  * Clears an existing timer.
  * Waits 450 ms.
  * Calls saveCurrentNote().

saveCurrentNote():

  PUTs the full title and blocks array.
  Updates the note's timestamp.
  Re-sorts the sidebar by newest update.

When switching notes, a pending save is flushed first.

When the page becomes hidden, a keepalive PUT attempts to save the current note.

Clear page:

  Removes visible blocks from the active note after confirmation.

Delete note:

  Deletes the SQLite note and its model conversation history after confirmation.


12. HEALTH AND CONNECTION STATUS
================================

checkHealth() calls /api/health during initialization.

Success:

  * Green online status.
  * "Desktop connected".
  * Router, chat, and image model names are shown.

Failure:

  * Offline status.
  * Error message shown in the sidebar.


13. SERVICE WORKER AND CACHING
==============================

The current cache name is versioned in frontend/service-worker.js.

Install:

  Cache the HTML shell, versioned CSS, versioned JavaScript, icon, and manifest.

Activate:

  Delete older InkNote shell caches and immediately claim clients.

Fetch:

  * Ignore non-GET requests.
  * Ignore /api/ requests.
  * Try the network first.
  * Update the cache with successful responses.
  * Fall back to the cache when the network fails.

Whenever app.js or styles.css changes, their query-string version and the service
worker cache name should also be incremented.


14. RESPONSIVE AND ACCESSIBLE UI
================================

The stylesheet adapts the sidebar, split canvases, toolbars, and scroll behavior for
desktop, tablet, and mobile widths.

Accessibility features include:

  * Semantic buttons and labels.
  * aria-live response/history regions.
  * aria-pressed tool and layout states.
  * Keyboard-accessible custom color field.
  * Visible focus styling.
  * Accessible generated-image download control.
  * Reduced-motion handling for image reveal.


===============================================================================
PART III - COMPLETE END-TO-END FLOWS
===============================================================================


A. CHAT REQUEST
===============

Browser CanvasPad
  -> white PNG + strokes
  -> POST /api/canvas/submit
  -> Qwen vision router returns action=chat
  -> process_user_message()
  -> semantic-memory lookup
  -> Qwen chat response
  -> save Qwen history
  -> API text_response
  -> assistant_text block
  -> diary fade-in
  -> SQLite autosave


B. IMAGE REQUEST
================

Browser CanvasPad
  -> white PNG + strokes + quality
  -> POST /api/canvas/submit
  -> Qwen vision router returns action=image and image_prompt
  -> clean recognized handwriting out of prompt
  -> FLUX text-to-image inference
  -> save data/generated/{uuid}.png
  -> API image_url with text_response=null
  -> assistant_image block
  -> image fade-in
  -> optional download icon
  -> SQLite autosave


C. TEXT AND IMAGE REQUEST
=========================

Browser CanvasPad
  -> POST /api/canvas/submit
  -> Qwen vision router returns action=both
  -> Qwen produces only separately requested written content
  -> FLUX produces the image
  -> one API result contains text_response and image_url
  -> both blocks receive the same turn_id
  -> AI canvas renders both together
  -> conversation exchange and visible blocks are saved


D. FAILURE FLOW
===============

Backend/model/network error
  -> non-success API response or thrown request error
  -> apiJson() creates a JavaScript Error
  -> pending assistant block becomes error
  -> original canvas strokes are restored
  -> toast is displayed
  -> UI is unlocked
  -> note is saved with the visible error block


===============================================================================
PART IV - COMMON EXTENSION POINTS
===============================================================================


Add a new backend route:

  1. Add a Pydantic request model in backend/app.py.
  2. Add the FastAPI route.
  3. Put business logic in a focused module rather than backend/app.py.
  4. Add an apiJson() call in frontend/js/app.js.

Add a new canvas action:

  1. Extend the action enum and router instructions in backend/services/image_generation.py.
  2. Add its execution branch in backend/agents/canvas_agent.py.
  3. Add new response fields to the API result.
  4. Add corresponding frontend block/rendering behavior.

Change image quality levels:

  Update all of:

    backend/app.py                         Literal validation
    backend/services/image_generation.py  Allowed inference values
    frontend/index.html                    Selector values
    frontend/js/app.js                     ALLOWED_INFERENCE_STEPS and friendly labels

Pass the canvas directly to FLUX:

  Do not do this casually. Previous image conditioning copied handwritten prompt text
  into the generated image. The current text-only FLUX path is intentional.

Add visible typography to generated images:

  The current notebook image route is intentionally text-free. A safe implementation
  should use a separate explicit UI field for exact scene wording rather than reusing
  handwritten instructions.

Change model names:

  Edit .env, then manually install the matching Ollama tags or Hugging Face
  repository. The application never provisions replacement models automatically.

Change frontend assets:

  Increment:

    /static/css/styles.css?v=...
    /static/js/app.js?v=...
    service-worker cache name
